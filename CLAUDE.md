# ZMW (zigbee2mqtt2web)

A set of generic home automation services talking over MQTT, each with a small web UI. Despite the name, not
just Zigbee: lights, sensors, heating, Sonos, Spotify, cameras, Telegram, TTS/STT, a local LLM assistant, etc.
See `README.md` for the list, the architecture and the MQTT topic map. Part of baticasa (see `../CLAUDE.md`).

## Layout

- `zzmw_lib/`: shared lib. Service base classes (`zzmw_lib/*mqtt*`), `service_runner`, web helpers (`www/`),
  and `z2m/`: the device proxy. `Z2MProxy` reads both `zigbee2mqtt` and `matter2mqtt` topics by default, so
  Zigbee vs Matter is transparent to services.
- `zmw_<name>/`: one service each; entry point is `zmw_<name>/zmw_<name>.py`, UI in `www/app.js`.
- `common.mk`: shared Makefile targets (`devrun`, `test`, `rebuild_ui`, `install_svc`, ...).
- `scripts/`: install/ops helpers, README/MQTT map generators, and `gen_unit.py`, which generates each service's
  systemd unit (see "Sandbox").

## Rules

- `zzmw_lib` is also used by `../baticasa`: grep it too when changing lib APIs.
- Service READMEs are regenerated from `get_mqtt_description()`; everything after `## MQTT` is overwritten.
  Keep prose above it.
- Don't run tests or `make rebuild_ui` on the dev machine; edit `www/app.js` only, never the built bundles.
- Don't read `config.json` / token caches: they hold live credentials. Use `config.template.json`.
- New deps go in the service's Pipfile / `rebuild_deps` target; don't probe local packages.
- UI: embed an app inside another (eg in the dashboard) with `z2mEmbedApp(App, App.buildProps(...))`, never a bare
  `React.createElement`, or its `on_app_became_visible` never runs. Poll with `mPoll` (pauses while hidden), and
  listen to visibility with `mOnVisibilityChange`; HTTP goes through `mAjax`/`mJsonGet`/... or `mFetch`, never raw
  `fetch`, so the net-down state stays right (for non-HTTP failures, eg a websocket closing, call `mNetProbe()`).
  An app polling with `mPoll` already refreshes on becoming visible (if a full interval went by while hidden):
  don't repeat that fetch in `on_app_became_visible`. Keep `on_app_became_visible` cheap: it runs on every tab switch.

## Sandbox

Every service runs in a systemd sandbox. Its unit is generated by `scripts/gen_unit.py` from
`scripts/unit_template.service` plus the service's `systemd.conf`; never edit a generated unit. A service only sees:
- read only: its own source dir and the source tree libs its Pipfile installs (`zzmw_lib`, `zext_libs/*`);
- read write: its run dir (`~/run/baticasa/<svc>`, its working dir and `$HOME`) and the shared scratch dir
  (`~/run/baticasa/tmp`);
- whatever its `systemd.conf` binds, from config.json keys (`BindPaths=@CFG:rec_path@`, `BindReadOnlyPaths=...`).
The rest of `/home` is hidden, the rest of the file system is read only, and `/tmp` is private to the service and
wiped when it stops. Other services' processes are invisible; there are no devices unless `systemd.conf` adds them.

So when a service needs a file or dir:
- Its own state, caches, models: relative paths, in its run dir.
- Anything another service reads by path (eg audio to transcribe, an image to send): a dir in the shared scratch
  dir, from a config key like the next item (eg TTS `output_dir`, homeboard `wakeword_dir`), never `/tmp` or
  `tempfile.gettempdir()`. The producer cleans up its own files there. The consumer opens it through
  `zzmw_lib.path_allowlist.PathAllowlist`, with the dir in its `allowed_paths`.
- Anything else (long term storage, eg `~/nvrish`): a path in config.json, never hardcoded. Read it as
  `cfg['key']` (required; `null` to disable the feature), add it to `config.template.json`, and bind it in the
  service's `systemd.conf` with `@CFG:key@` (install fails if the key or the path is missing).
- After changing `unit_template.service` or a `systemd.conf`, run `make update_units` (then restart the services).
